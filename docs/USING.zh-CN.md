# Commerce 使用与支持

[English](USING.md) · **简体中文**

## 何时使用

仅当产品需要持久的支付到权益编排时使用 Commerce。它是一个无界面服务，具有明确渠道与 Permit 签发边界；不是支付机构、MoR、身份系统，也不证明商户准入。

## 要求与成熟度

需要 Racket CS 9.0+ 和运行手册声明的部署依赖。首个渠道路径为 Pancake；夹具和正在运行的 SQLite 进程不能证明真实购买、结算或合规就绪。产品和商户审核属于独立开卖门禁。

## 一次有效验证

配置渠道秘密前先运行模拟 walkthrough。真实运营需鉴权 webhook 精确字节、持久化日志、事务内投影，并从 outbox 签发。支付跳转不是支付证据。备份恢复需包含 SQLite 日志、投影、outbox，以及单独保护的签发材料；不能靠猜测重放结果未知的操作。

## 升级、数据与支持

固定并记录应用实际测试的包版本和平台。升级前阅读 CHANGELOG 与兼容契约，在副本上测试用户数据迁移，并保留可恢复版本。框架或库不替产品提供数据库备份、发布证书、退款、账号恢复或隐私政策。不要把示例夹具中的客户、商品和金额当成真实 offer。

在 [Issues](https://github.com/turlamai/commerce/issues) 反馈，中文或英文均可。包含包版本/提交、Racket 版本、系统架构、最小复现和已脱敏的首条错误。不要附带真实密钥、客户凭据、支付原始数据或私密文档。社区支持不承诺响应时限。

[安全边界](security.md)包含服务秘密与数据处理要求；
疑似漏洞按[私密报告流程](../SECURITY.md)反馈，
[发布证据清单](release-checklist.md)区分夹具验证与生产准入。
公开 Issue 只提交无敏感信息的复现。
